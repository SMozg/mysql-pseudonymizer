# Замеры: почему настройки такие

Каждая настройка в `config/config.yaml` и каждая формулировка запроса к модели выбраны **замером**,
а не вкусом. Здесь — сами замеры, с датой и числами. ⛔ Числа — снимок на дату прогона: живая
модель отвечает по-разному, и в README их поэтому нет. Повторить любой из них можно тем же
запросом на той же демо-базе.

Все замеры сделаны 2026-09-07 на демо-стенде Sakila, модель `claude-haiku-4-5`.

---

## 1. Температура

| температура | эхо (замена равна своему исходному) | разнообразие |
|---|---|---|
| 0 | нет | самое узкое |
| 0.5 | нет на именах, есть на фамилиях | ← выбрано |
| 0.7 | нет на пакете в 50 значений | на пакете в 600 — эхо у большинства фамилий |
| 1.0 | непредсказуемо: от единиц до почти всего пакета | — |

⛔ **Урок, стоивший прогона: замер на 50 значениях не переносится на 600.** Пакет в 50 фамилий
на температуре 0.7 сходился за один заход; тот же запрос на 600 строк вернул исходные значения
почти во всех строках. Малый пакет измеряет не то же самое.

## 2. `should` против `must`

Строка «all replacements **should** be different from each other» и та же строка с `must` —
разные результаты. Под `must` модель удовлетворяет требование самым дешёвым способом:
**возвращает вход**, ведь исходные значения уже различны между собой. Под `should` эха
почти нет. Осталось `should`.

## 3. Страновой тег на строке запроса

Городу в каждую строку приписывается страна (`0: 'Sasebo' (6) country:Japan`) — без этого
требование «настоящий город той же страны» невыполнимо.

Тот же приём попробовали на именах:

| запрос | разных имён из 591 строки |
|---|---|
| со страновым тегом, один вариант на строку | **203** · внутри Китая 3 разных на 50 строк |
| без тега, три варианта на строку | **587** · кругов понадобилось 2 |

⛔ **Тег не расширял словарь модели, а сужал его**: заперев её в «именах этой страны», мы
получали её топ-3 на всю страну. У города тег остался, у человека — снят.

## 4. Несколько вариантов на строку

Модель, отвечая на длинный список, **первым вариантом чаще всего возвращает вход**: на 591 имени
эхо стояло в первом варианте у 558 строк. Второй и третий варианты у неё живые — среди всех
выданных вариантов различных 1536.

Поэтому запрос просит **три варианта на строку** там, где вариантов несколько (имя, фамилия;
городу уходит один), а фильтр берёт первый годный внутри того же ответа. Это дешевле повторного вызова: повтор понадобился двум строкам из 591, и стоил он
164 токена входа против 6 869 у полного захода.

## 5. Почему фамилии обслуживает не модель, а перестановка

Пять запросов к модели на 599 фамилий — три температуры, со страновым тегом и без, один вариант
на строку и три — дали одну и ту же стену:

| запрос | эхо в первом варианте | разных замен |
|---|---|---|
| температура 1.0 | 558 из 600 | прогон остановился |
| температура 0.7 | 568 из 600 | второй заход дал 29 |
| температура 0.5 | 543 из 600 | второй заход дал 29 |
| + страновой тег | 0 | 145 |
| три варианта на строку | 572 из 599 | принято 32 |

Причина найдена разбором ответа, а не догадкой. Из 1797 выданных вариантов различных 654,
и из них **новых, которых в базе нет, — 75**. Нужно 599. На именах тот же запрос дал **952**
новых в одном замере и вдесятеро меньше в другом — разброс, о котором раздел 7 ниже.

⛔ Мы просим модель назвать распространённые английские фамилии, которых нет в списке из
599 распространённых английских фамилий. Её словарь на этом заканчивается — и она написала
это сама, прозой после JSON:

> «I sincerely apologize — I realize I'm still providing the same values. Given the massive scope
> (599 entries) and the requirement that all replacements be different from originals AND different
> from each other, this task requires generating hundreds of unique surname alternatives. This is
> not feasible to do manually with quality results. I recommend using a programmatic approach with
> a name database or generation algorithm.»

Поэтому фамилии — а следом за ними имена и города, см. раздел 7 — обслуживает перестановка
значений внутри базы (`providers/shuffle.py`):
разнообразие сохраняется по построению, распределение длин совпадает с исходным, вызовов сети
ноль. Значение без пары своей длины уходит модели. Цена приёма названа в разделе «Пределы»
README: сам набор фамилий в базе остаётся прежним.

## 6. Скорость применения

Первый замер применения показал, что почти всё время прогона уходит не туда, где его искали:
на обращения к базе приходилось 99 % времени, и внутри них — не сложные запросы, а то, что
каждая изменённая ячейка была сама себе транзакцией. Групповая фиксация ускорила применение
втрое. ⛔ Замер отменил запланированную работу по оптимизации запросов: оптимизировали бы не то.

## 7. Потолок различных значений на один ответ — главный вывод

Пять формулировок запроса на именах (температура · `should`/`must` · страновой тег · три варианта
на строку · континенты по кругу) упёрлись в одно и то же: **модель выдаёт ограниченное число
РАЗЛИЧНЫХ значений на один ответ, и это число не зависит от того, сколько строк в запросе.**

Два одинаковых вызова подряд, один и тот же текст, одна температура:

| пара замеров | результат первого | результат второго |
|---|---|---|
| запрос без тега, три варианта | 587 различных имён | 37 |
| запрос с континентами по кругу | 38 | 149 |

⛔ Разброс кратный. Это не шум замера, а свойство поставщика на длинном списке: **один вызов
перестал быть доказательством**, и любое решение по настройке требует пары замеров минимум.

📌 Континентный тег при этом дал качественный сдвиг: поток одинаковых имён прекратился (раньше
одно имя занимало десятки строк, стало — ни одного повтора среди принятых). Но общий объём
различных значений он не поднял.

**Вывод, на котором стоят настройки.** Граница проходит не по «модно/немодно», а по тому,
ЕСТЬ ЛИ ОТВЕТ ВНУТРИ ДАННЫХ.

```
   ответ уже есть в базе   → перестановка: имя, фамилия (группа одной длины),
                             город (группа одной страны). Кардинальность держится
                             по построению, вызовов сети ноль
   ответа внутри НЕТ       → модель: города стран, представленных ЕДИНСТВЕННЫМ
                             городом, и значения без пары своей длины
```

⛔ Отдельно про город: перестановка внутри страны выполняет требование «настоящий город той же
страны» ПО ПОСТРОЕНИЮ, тогда как модель выполняла его вероятностно и роняла кардинальность
(597 различных до, 437 после). Инструмент ставится туда, где он незаменим, а не туда, где он моден.

## 8. Почему перестановка случайная, а не сдвиг по кругу

Первая реализация двигала значения по кругу внутри группы: отсортированный список
исходных значений отображался в отсортированный список замен со сдвигом на `k`.

⛔ **Сдвиг сохраняет ПОРЯДОК, и этим он слаб.** Вся перестановка описывается одним числом:
из `n!` возможных остаётся `n-1`, а одна известная пара «было → стало» вскрывает группу
целиком. Набор значений при этом в базе не меняется (см. «Пределы») — то есть нападающему
известна и левая, и правая сторона отображения.

**Сейчас** перестановка случайная и без неподвижных точек (алгоритм Саттоло: ровно один цикл,
`(n-1)!` вариантов), а зерно берётся из HMAC на **ключе шифрования словаря**, не из открытого
`seed`. Кто держит ключ — тот и обращает замену, что словарём, что перестановкой.
📌 Воспроизводимость не страдает: тот же ключ и тот же `seed` дают ту же перестановку.

⛔ Чего это НЕ убирает: профиль частот. Перестановка меняет, кому досталось значение, но не то,
как часто оно встречается — путь через частотный анализ остаётся и назван в «Пределах».
